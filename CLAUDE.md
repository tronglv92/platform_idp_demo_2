## Project Overview

This is a **platform IDP (Internal Developer Platform)** repository containing two components:
- **go-service-template/** — A production-grade Go microservice boilerplate built on [go-zero](https://go-zero.dev/) with gRPC + REST (gRPC-Gateway), serving as a template for new services
- **backstage/** — Backstage integration (minimal, early stage)

The go-service-template exposes three independent service entrypoints: HTTP/gRPC server (`cmd/main`), message consumer (`cmd/consumer`), and cron scheduler (`cmd/cron`).

## Common Commands

All commands run from the `go-service-template/` directory. The Makefile sources `.env` automatically.

```bash
# Start infrastructure (Postgres, Redis, Kafka, Jaeger)
docker compose up -d

# Run the main HTTP/gRPC server
make run

# Run the cron scheduler (optionally pass a specific command)
make cron

# Run the message consumer (Kafka or RabbitMQ based on QUEUE_STACK in .env)
make consumer

# Run tests with coverage
make test

# Generate HTML coverage report
make coverage

# Generate all proto code (gRPC stubs + HTTP transcoding + OpenAPI + validation)
make all

# Generate gRPC code only
make grpc

# Generate validation code only
make validate

# Generate OpenAPI v2 (Swagger) spec
make oswagger

# Generate mocks (uses mockery)
make mocks

# Install proto toolchain (protoc plugins, goctl, grpcurl)
make init
```

To regenerate the service factory after adding/changing services or repositories:
```bash
pmctl gen service
```

## Architecture

### Layered Structure (go-service-template/internal/)

```
handler/          → Transport layer (gRPC + REST handlers, thin: validate → call service → respond)
service/          → Business logic layer (interfaces + implementations)
repository/       → Data access layer (GORM-based, only layer that touches DB)
types/
  entity/         → Database models (GORM tags, migration registration)
  dto/            → Request/response data transfer objects
  mapper/         → Entity ↔ DTO transformations
  define/         → Constants and enums
consumer/         → Kafka/RabbitMQ message handlers
cron/             → Scheduled job definitions
config/           → YAML config loading with env var substitution (go-zero conf)
registry/         → Composition root / dependency injection (see below)
```

### Registry Pattern (Dependency Injection)

The `registry/` package is the **composition root** — it wires all dependencies. No business logic belongs here.

**Context hierarchy:**
- `BaseContext` — Config, cache, queue producer, downloader (shared by all runtimes)
- `RepositoryContext` — Database repositories
- `SecurityContext` — Composed from Authentication + Authorization + HTTP security contexts
- `ServiceContext` = Base + Security + Repository + ServiceFactory (used by HTTP/gRPC server)
- `ConsumerContext` = Base + Repository (used by message consumer)
- `CronContext` = Base + Repository (used by cron scheduler)

Each runtime (server/consumer/cron) gets only the dependencies it needs. Heavy dependencies use lazy initialization via `oncex.OnceValue`.

### Service Factory (Code-Generated)

`service/service_factory.go` is **generated by pmctl** — do not edit manually. It scans `*_service.go` constructors, resolves their dependencies from context interfaces, and generates lazy-initialized getters. Configured in `pmctl.gen.yaml`.

### Proto / API Layer

Proto files live in `api/<service>/`. The generation pipeline (`make all`) produces:
- `*.pb.go` — Protobuf messages
- `*_grpc.pb.go` — gRPC server/client stubs
- `*_http.pb.go` — REST route registration (gRPC-Gateway style via custom `protoc-gen-go-http`)
- `*.pb.validate.go` — Request validation
- `*.swagger.json` — OpenAPI spec

REST routes are prefixed: `/boilerplate-svc/api/v1/...`

### Helper Library (go-service-template/helper/)

Shared infrastructure library (referenced as a Git submodule). Key packages:
- `server/` — HTTP/gRPC server bootstrap, middleware, interceptors
- `db/` — GORM database adapter with read replica support, cursor pagination
- `cache/` — Redis wrapper
- `queue/` — Kafka and RabbitMQ abstraction (producer/consumer)
- `authenticator/` — JWT/JWKS authentication
- `authorizer/` — Permission-based authorization
- `security/` — Security route registration, permission matching
- `errors/` — Standardized error definitions
- `toolkit/` — Utility packages (oncex, cryptox, stringx, timex, etc.)

### Database

Production uses **PostgreSQL** managed by [CloudNativePG](https://cloudnative-pg.io/) on Kubernetes. The GORM-based data access layer (`helper/db/`) supports read replica routing. Local dev uses standard PostgreSQL via Docker Compose.

### Configuration

Runtime config: `etc/app.yaml` with `${ENV_VAR}` substitution. Environment defaults in `.env`.

**Ports (local dev):** HTTP 8082, gRPC 8083 | Postgres 5433, Redis 6380, Kafka 9093, Jaeger UI 16687

## Conventions

- **File naming:** `*_service.go`, `*_repository.go`, `*_handler.go` — these patterns are scanned by pmctl for code generation
- **Constructor naming:** `New<Name>Service`, `New<Name>Repository` — must follow this pattern for pmctl scanner
- **Adding a new domain entity:** Create entity in `types/entity/`, DTO in `types/dto/`, mapper in `types/mapper/`, repository in `repository/`, service in `service/`, handler in `handler/`, then run `pmctl gen service` to update the factory
- **Proto changes:** Edit `.proto` files in `api/`, then run `make all` to regenerate. Run `protoc-go-inject-tag` if custom struct tags are needed
- **Generated files:** Never edit `*.pb.go`, `*.pb.validate.go`, `*_grpc.pb.go`, `*_http.pb.go`, or `service_factory.go` directly
- **Go module:** Module path is `go-service-template` (not a URL-based module path)
- **Vendor mode:** Dependencies are vendored in `vendor/`
